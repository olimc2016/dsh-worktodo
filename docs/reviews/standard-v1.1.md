## 1. 结论先行

v1.0 已经把"平台包只能 optional peer"写成一条规则，但它缺三样东西：

1. **机制**：为什么一份硬依赖能让整个桌面版起不来（hoisted 摊平 → 本层优先 → 闸门 disable → disable 行不进 pending）。只写"不要这么做"，下一个人仍会问"为什么"。
2. **配套规则**：宿主版本对齐、自更新事务、启动期纪律、错误隔离、可观测性 —— 这五块在 0.2.5–0.2.8 各自出过事故，v1.0 一条都没写。
3. **防线归属**：事故表只有"根因 + 条款"，没有"下次是哪条断言拦住它"。于是"复盘"读起来像故事，落不到门禁上。

v1.1 补齐这三样，并把事故表重做成 **§6 事故档案**：8 条主事故，每条都写"怎么自动拦住"。

## 4. 新增 / 改写的关键句

**§2.7（机制，回答"为什么"）**
- "**任何硬依赖都会被摊平进 profile 顶层** ✗"、"**profile 层解析优先于宿主安装层** ✗"、"**宿主有兼容性闸门** ✗"、"**被 disable 的行不出现在 pending 名单里** ✗ —— 服务提供者凭空消失，下游全部等待"。
- "crash 日志里既没有 `Failed plugins` 段、也没有 disable 行，所以从用户能拿到的日志**看不出真因**。"
- "**静态断言证明不了'装出来只有一份'**：必须再做一次 §4.1 的 profile 模拟。"

**§2.8（宿主版本对齐）**
- "**宿主升级 = 插件的回归事件**：插件'一行没改'也可能装坏宿主——2026-10-18 就是宿主先升级、插件后安装。"
- "`devDependencies` 的精确版本只是**测试夹具**……不随发布包出去。"

**§2.9（自更新事务，从 0.2.7 六条提炼）**
- "自更新是插件里唯一会**改用户环境**的代码路径，默认假设它会失败。"
- "**win32 回退不得先删目标** —— 先落 `.bak`、再删、再 rename；二次失败从内存/备份恢复；恢复不了就**保留 `.bak` 并把路径写进错误**。"
- "`package.json` 与 `pnpm-lock.yaml` 属**同一事务**……回滚漏 lockfile = 用户下次装到一半。"
- "**卸载后零写盘、零子进程**……卸载后连回滚也不写。"
- "**profile 定位只从模块自身路径推**……取**最后一个**段，**推不出就零写盘失败**，绝不指到外层 profile。"
- "'成功'只认**落盘版本变了**，不认退出码。"
- "CLI 明确拒绝（`active-run` / `incompatible`）必须 **failed 并停止序列**，**绝不降级到 pnpm** 绕过宿主保护。"

**§2.10 / §2.11 / §2.12**
- "**任何'自动修改用户环境'的动作默认关闭**，或必须用户显式开启。"
- "每个 `void promise` / `.then()` 必须有 `.catch` —— 宿主进程里 unhandled rejection 就是一次未捕获异常。"
- "降级必须**显式可查**……不许'看起来正常但少了能力'。"
- "**不要把关键信息只写进会被丢弃的日志**。"

**§3**
- "`node tools/verify-all.mjs | tail -20` 的 `$?` 是 `tail` 的，基线 9/10 的失败会被整段吞掉。"
- "**本地碰巧绿**也是缺陷。"
- "元测试要**扫全文**：只盯已知位置或白名单必然还会漏。"
- "React 替身如果不重渲染/不走渲染期，就会漏掉'黑屏'类 bug。"

**§4**
- "目标**不是'能装上'**，而是**装出来只有一份平台包，且解析到宿主那份**。"
- 反向样本断言（把平台包塞回 `dependencies`，第 1、3 条必须变红）。

**§5**
- "**批准前必须完成 §4 全部验证**：暂存区不是'先占位、后补验证'的地方。"
- "**先 `npm dist-tag add <pkg>@<good> latest`** —— 用户的自动更新（唯一依据是 `latest`）立刻停止拿到坏版本。"
- "72 小时内 `npm unpublish <pkg>@<ver>`；超过 72 小时只能 `deprecate`；同一版本号不可重发。"

**§6**
- "每条都必须能回答：**'下次同样的事，是哪条断言/哪道闸门把它拦住？'** 答不出来的事故 = 还没沉淀完。"
- "事故 1 与 2 是同一个坑的两面……正确位置只有一处：**optional peer + 函数内动态 import + 失败降级**。"

## 5. 自动防线现状（诚实版：哪些真自动，哪些还是人）

| 防线 | 状态 | 在哪 |
|---|---|---|
| `dependencies` 无 `@deepseek-ai/*` + optional peer + 顶层无静态 import + 动态 import 集合一致 | ✅ 自动（含反向自检） | `verify-submission`，`prepublishOnly` / CI |
| 构建失败即红（不测旧产物） | ✅ 自动 | `verify-all` 第一步 |
| 版本号字面量元测试 | ✅ 自动 | `smoke-host` |
| 平台包缺失时 `apply` 不抛、只降级 | ✅ 自动 | `smoke-host` 子进程用例 |
| 自更新：进程树 / dispose / 锁 / 原子写 / lockfile 事务 / CLI 拒绝不降级 | ✅ 自动（各自有反向验证） | `smoke-host` B1/B2/B3/C1/C2/B4 |
| Windows 执行器 / 路径 / rename / 进程树 | ⚠️ 模拟自动，**无真机** | `smoke-host` + `WORKTODO_PLATFORM` |
| 双环境 + 显式退出码 | ⚠️ 靠人按清单执行（命令已写进 §3.2.6/§4） | 文档 |
| **profile 模拟安装** | ❌ **手工**（§4.1 四条断言） | 文档 checklist |
| **宿主升级模拟** | ❌ **手工**（§4.2） | 文档 checklist |
| 真 React + DOM 渲染 | ❌ 未落地（迷你渲染器替代） | §3.3 缺口 |

结论：**8 条主事故里，5 条（1/3/4/6/8）的防线完全自动；1 条（2）是"静态断言自动 + profile/升级模拟手工"；2 条（5/7）是半自动（有模拟用例，缺真 DOM / 真机 Windows）。** 手工与半自动的部分，就是下一版最该补的。

## 7. 还没覆盖到的空白（建议下一版补）

1. **profile 模拟没有脚本**。§4.1 现在是手工 checklist，最容易在"赶发版"时被跳过。建议做成 `tools/verify-profile.mjs`：临时目录 + 假宿主层 + 真 tarball + 四条断言 + 反向样本，一条命令给结论；最好进 `verify-all`（但会引入 pnpm 依赖，需要设计成"检测到 pnpm 才跑，否则显式 skip 并打印原因"，不能静默跳过）。
2. **宿主升级模拟同样手工**，而且需要两套 complete installation 闭包（0.2.1 的部分平台包没全发到公共 registry，本机拼不出来）。这条短期只能靠"用户真机 + 诊断"，中期应做成"用假平台包冒充两个版本"的形状测试（能覆盖解析顺序，覆盖不了真实兼容性闸门）。
3. **没有真 React + DOM 的渲染测试**。迷你渲染器抓得到"渲染期抛错/边界兜底"，抓不到 `setState` 重渲染、并发渲染、浏览器 API 差异。验收标准已写死（改坏 `setState` 分支必须红），但实现还没做。
4. **"环境变量在调用时读"无法静态检查**。现在只有约定 + 一条慢 registry 时序用例；如果新增开关又写成模块级常量，没有门禁会红。
5. **真机 Windows 仍然缺**。`taskkill /T /F`、`MoveFileEx`、杀软占用 `rename` 都只是形状测试。
6. **`latest` 与自动更新的耦合没有测试**。§5.6 写了"`latest` 是唯一依据"，但仓库里没有用例断言"dist-tag 指向旧版本时插件不会报有新版本"——这属于发布面，可能需要一个假的 registry 夹具。
7. **§4 的数据对账条款仍偏 token 面板**（金额/窗口）。worktodo 只需要"条数与分组自洽"，两套插件的验收项没有分叉写清；未来可拆成"通用条款 + 按插件补充"。
