# 子待办（subtasks）+ 备注（notes）：设计与预览

- 状态：**待用户拍板**（本轮只做设计与静态预览，**未改应用代码**、未升版本、未改 CHANGELOG / `.github`、未 commit / push / tag / 发布）
- 对象：`~/Documents/deepseek-harness/default-workspace/dsh-worktodo`
- 配套预览：`docs/design/subtasks-notes.html`（本地 URL 见 §9；纯前端假数据，不写文件、不发请求）
- 一句话：**子待办内嵌在记录里（`subtasks: []`，≤50 条）；备注沿用现有 `notes`（2000 字，纯文本、保留换行）；交互推荐「A 行内展开管子待办 + B 右侧抽屉管备注」；勾完最后一条不自动完成父项，只给轻提示。**

---

## 1. 结论（先看这 8 条）

1. **子待办用内嵌数组**，不做独立记录 + `parentId`（理由与代价见 §3.1）。
2. **子待办不带自己的日期 / 优先级 / 项目 / 备注**；需要这些信息就升级成一条独立待办。保持「父项是一个可执行事项，子项是它的检查清单」。
3. **备注不是新字段**：`notes` 已经存在于记录、`patchRecord`、编辑表单、搜索里；本轮补齐的是**列表可见性与快捷入口**，不是重新造字段。现有上限 **2000 字**建议保持不变（不改成 5000）。
4. **推荐交互 A+B**：`2/3` 进度 chip 点开**行内清单**（A）；备注图标点开**右侧抽屉**（B）。抽屉里同时给标题/日期/项目/优先级等上下文，但子待办勾选仍回行内做。
5. **父项勾选 → 子项全勾**（单向级联）；**取消父项 → 只取消父项**，子项保持原状。
6. **勾完最后一条子待办 → 父项不自动完成**，只在清单底部出现一次轻提示「全部完成，要勾掉这条吗？」；`先不` 后本次不再打扰。
7. **上限**：子待办 **50 条/父**；子待办标题 **200 字**（与父标题同口径，UI 建议一行内）；备注 **2000 字**。错误沿用 `WorkTodoError(reason, message)` + HTTP 200 `{ok:false, reason, message}`。
8. **兼容**：老数据没有 `subtasks` → `[]`，没有 `notes` → `''`；`repairRecord` 对坏数组做「过滤 + 补 id + 截断到 50」的宽容修复，不因为一条坏子待办把整条记录丢掉。

## 2. 现状与目标

### 2.1 行结构（`src/client/index.js`）

当前单行结构是：

```
[旗子槽 18px][勾选 26px][标题 flex:1][小字组：日期/来源/已过期/项目][行尾操作：铅笔/删除]
```

- 标题被截断时整行切网格，小字组落到第二行、右对齐（`.wt-row--wrap`）。
- 小字组 chip 的顺序固定为 `[date][source][overdue][project]`；有内容才渲染，chip 之间 6px。
- 行尾操作平时 `opacity:0; pointer-events:none`，hover / `focus-within` 才显形（键盘仍可 Tab 到）。
- 完成动效约 1.23s：勾选框呼吸 → 对勾描边 → 整行淡出；面板会延迟刷新到动效播完。

### 2.2 备注已经在，但藏在铅笔里

- 数据：`notes` 是顶层字段，`normalizeNotes` 去首尾空白、上限 **2000**，`createRecord` 默认 `''`，`patchRecord` 已接受 `notes`。
- UI：只有点行尾铅笔进入整单编辑表单，才会看到备注 textarea；列表行上**没有任何提示**。
- 搜索：`/list?query=` 已经同时匹配标题与 `notes`（`src/service.mjs`）。
- 统计：`statsOf` 只按父记录计数，不数备注。
- 结论：备注的「数据模型 + 写入协议 + 搜索」都已就绪；缺的是**列表可见性**与**不打断勾选的编辑入口**。

### 2.3 本轮目标 / 非目标

**目标**

- 一条待办可以带一份**有序检查清单**，能勾选、改名、删除、新增，进度一眼可见。
- 备注在列表行有痕迹、可一键打开编辑；长文本有足够空间。
- 老数据无损、老客户端不崩、导出/搜索口径明确。

**非目标（本轮明确不做）**

- 子待办的子待办（不做递归）。
- 子待办独立日期 / 优先级 / 项目 / 备注 / 负责人。
- Markdown、富文本、附件、@提醒。
- 独立记录 + `parentId` 的存储方案（只在 §3.1 对比，不实现）。
- agent 工具直接编辑子待办（放第二阶段；第一阶段 agent 只读得到）。
- 甘特/看板/依赖关系。

## 3. 数据模型

### 3.1 子待办：内嵌 vs 独立记录

| 维度 | (a) 内嵌 `subtasks[]`（推荐） | (b) 独立记录 + `parentId` |
| --- | --- | --- |
| 存储 | 父记录多一个数组字段 | 同一个 todos 表加一种「子记录」，或新表 |
| 读取 | 一次 `/list` 就带全，进度直接算 | 要按 `parentId` 组装；列表要么不带子项、要么 N+1 |
| 写入 | 一次 `update`，整数组原子替换 | 每条子项单独 create/update，失败会半套 |
| 一致性 | 父在子就在，删父即删子 | 可能出现孤儿；删父要级联清理 |
| 排序 | 数组顺序 / `order` 字段 | 子项各自 `order`，还要跨父排序 |
| 搜索 / 统计 | 天然不增加父记录数；统计=1 条 | 必须处处排除 `parentId` 记录，容易漏 |
| 迁移 | 新字段，缺省 `[]`，零迁移 | 要处理旧记录、孤儿、重复父、视图口径 |
| 子项独立字段 | 不支持（刻意） | 支持，但产品复杂度陡增 |
| 载荷 | 每个父多几十~几百字节；50 条上限可控 | 列表不多带，但详情要额外请求 |
| 适用 | 单用户、单机、检查清单式任务 | 多人协作、子项需要独立生命周期/负责人 |

**推荐 (a) 内嵌**。理由：本插件的核心是「一个人的工作清单」，子待办是父项的检查步骤，不是独立任务；内嵌让「勾选父项/子项、进度、删除、导出」都变成一次纯函数变换，且不需要任何迁移。独立记录只有在「子项要独立分配、独立截止、独立被搜索/统计」时才值得，那已经超出本轮范围。

**已知代价（接受）**：

- 一次 patch 传整个数组，两个窗口同时改同一条父项时后写覆盖先写（单用户本地场景风险低；第二阶段可加 `subtaskOp` 原子操作）。
- `/list` 载荷会变大。按 50 条 × 约 40–80 B 估算，最坏每条父项 +2–4 KB；典型 3–5 条只有 +150–400 B。若未来 5000 条都塞满，再考虑「列表只回 counts + 详情路由」。
- 不能对子项单独建索引/搜索（第二阶段若需要，可在内存里展开）。

### 3.2 子待办形状与约束

```jsonc
// 记录（只列新增字段）
{
  "id": "wt-...",
  "title": "整理评审意见",
  "notes": "评审重点：\n1. ...",          // 已有字段，不改位置
  "subtasks": [
    { "id": "st-m1k2-7f3a", "title": "整理会议记录", "done": true,  "order": 0 },
    { "id": "st-m1k2-8b1c", "title": "汇总三条争议", "done": false, "order": 1 }
  ]
}
```

| 字段 | 规则 |
| --- | --- |
| `id` | 非空字符串，父项内唯一；客户端生成 `st-<base36 时间>-<4 位随机>`。不需要全局唯一（但实际也很难撞）。 |
| `title` | `trim` 后非空，≤ **200** 字（复用 `TITLE_MAX`，不另造一套）；纯文本。 |
| `done` | 严格布尔；`true` = 完成。写入时只接受布尔，读盘修复时把非 `true` 一律当 `false`。 |
| `order` | 有限整数 ≥ 0；写入时按它排序后**重排为 0..n-1**，缺省按数组下标。 |
| 数组上限 | **50 条/父**；达到上限后 UI 隐藏「添加」，服务端拒绝第 51 条。 |
| 递归 | 不允许；子项对象里出现 `subtasks` 字段直接忽略（不报错，避免老数据/手改数据打不开）。 |
| 子项额外字段 | 不允许（不存 `due` / `priority` / `notes` / `project`）；出现也不读。 |

**排序口径**：数组顺序是唯一真相；`order` 只是显式排序的载体（导入/手改时用），写入时先按 `order` 稳定排序再重编号。读取时若 `order` 缺失按数组顺序。

**为什么不允许子项有自己的日期/优先级**：一旦允许，子项就变成「另一条待办」，用户会问「父项的截止和子项的截止谁算数」「按日期分组时子项去哪」「逾期统计算不算子项」——每个问题都要新规则。保持「父项负责时间/优先级/项目，子项只负责勾」最省认知，也最符合检查清单的心智模型。需要独立时间的事项，直接建一条独立待办。

### 3.3 备注

| 项 | 取值 / 规则 |
| --- | --- |
| 字段位置 | 顶层 `notes`，字符串，不嵌进 `subtasks` |
| 默认值 | `''`（沿用现有；**不建议改成 `null`**，会让现有读取路径和测试多一套分支） |
| 内容 | 纯文本；**保留内部换行**；不支持 Markdown / HTML；首尾空白 `trim`；建议把 `\r\n` 归一成 `\n` |
| 上限 | **2000 字**（现有 `NOTES_MAX`；不改成 5000） |
| 计数口径 | 与现有 JS `String#length` 一致（UTF-16 code unit；emoji 算 2）。UI 显示 `123 / 2000`。 |
| patch | `{ "ref": "wt-...", "notes": "..." }`；`notes: ""` 表示清空 |
| 错误码 | `bad-notes`（不是字符串）、`notes-too-long`（超上限）；均为 200 + `{ok:false}` |
| 搜索 | **带上**（现有行为，保留）：标题或备注包含关键词即命中 |
| 统计 | **不算**：备注不产生条目、不影响 open/overdue/today |
| 导出 | 若将来有导出，原样带 `notes`（不截断、不改换行）；当前没有独立导出路由，JSON 存储本身已包含 |
| 展示 | 行上只显示一个小图标 + 是否有内容的点；不把正文塞进行内，避免撑高单行 |

**为什么保持 2000 而不是 5000**：上限是已经写进 `records.mjs`、工具描述和用户心智的数据契约；改大本身不需要迁移，但会让「保存失败」的边界移动，且没有证据表明 2000 不够。若用户明确要长笔记，第二阶段只改常量 + 文案 + 用例即可，不动存储形状。

### 3.4 派生值（不落库）

```js
// 纯函数，服务端/客户端/测试共用同一份口径
subtaskProgress(record) -> { total, done, allDone, ratio }
```

- 只在渲染/统计时计算，**不存** `doneCount` / `progress`，避免两处真相。
- `allDone` 仅在 `total > 0` 时为 `true`；空清单不算「全部完成」。
- 统计：父项仍算 1 条；子项**不计入** open/overdue/today/completed 任何数字。
- 搜索（建议）：父标题 + 备注 + **子待办标题**。子项命中时返回父项；这是「我明明记得清单里有这个词」的自然预期，成本只是一次数组遍历。

## 4. 交互设计

### 4.1 三个方案与推荐

| 方案 | 子待办 | 备注 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| **A 行内展开** | 点 `2/3` chip，行下展开清单；父行保持单行 | 仍在铅笔表单里（本轮不解决） | 勾选/改名不离开上下文，连续勾最快；父行高度不变 | 展开推高列表；320px 下缩进后横向空间紧；长清单要滚 |
| **B 右侧抽屉（全部放 B）** | 点 `2/3` 或备注图标 → 抽屉里勾 | 抽屉内多行 textarea | 一个详情面收全部信息；备注空间充足；窄屏全宽 | 每次勾子项都要开关抽屉，核心循环变慢；抽屉遮住列表，无法边看边勾 |
| **A+B 组合（推荐）** | A：行内清单 | B：抽屉只负责备注 + 只读上下文 | 各自最顺手：勾选留在行内，备注有足够空间；入口分工清楚 | 要学两种展开方式；行尾多一枚备注图标，320px 更挤（靠换行兜住） |

**推荐 A+B，而不是全部放 B**：子待办的高频动作是「勾一下」，它必须零导航；备注是低频、长文本、需要空间的动作，抽屉更合适。全部放 B 会把最高频动作塞进最重的容器里。

**方案 A 单独也能成立**：如果只想先做一半，先做 A（子待办）收益最大；备注继续走现有铅笔表单，等 A 稳定后再加 B。

### 4.2 行内新增的零件

```
[旗子][勾选][标题 ................][日期][已过期][2/3][#项目][备注图标][铅笔][删除]
                                      └──────── 小字组 chip ────────┘  └ 行尾操作 ┘
```

- **进度 chip `2/3`**：和日期/项目同一套 `.wt-tag` 胶囊视觉（10.5px、圆角 999、1px 边框），前面一枚 11px 清单图标。
  - 有子待办才渲染；`0/3` 也显示（让人知道有清单）。
  - 全部完成时用 `ok` 色 + ok 淡底/淡边；未完成用 `label3`。
  - 可点：A/AB 展开/收起行内清单；B 打开抽屉。
  - `aria-label="子待办 2/3，展开"` / `"Subtasks 2/3, expand"`；`aria-expanded` 跟随；滚动到可见区域不强制。
- **备注图标**：19–22px 的小图标按钮，放在行尾操作组里（不占小字组的 chip 位）。
  - 有备注：常显，实色，右上角一个 4px 的品牌色小点。
  - 无备注：平时透明，行 hover / focus 时淡出（与「＋日期」「＋项目」同一套 hover 语言）。
  - 点击：B/AB 打开抽屉并聚焦 textarea；A/现状没有这个入口（备注仍走铅笔）。
  - `aria-label="备注（有内容）"` / `"添加备注"`。
- **`＋子待办`**：没有子待办时，在小字组末尾出现一枚虚线胶囊（hover/focus 才可见），点击直接展开并聚焦新增输入；不常驻、不挤行尾操作。
  - B 方案里它打开抽屉并聚焦「添加子待办」输入。
  - 达到 50 条后不再显示，改为清单底部一句「已达 50 条上限」。
- **行尾操作**：仍只有铅笔/删除；B/AB 多一枚备注图标。**不把「＋子待办」塞进行尾**，否则 320px 下四个 22px 图标会把标题挤没。

### 4.3 行内清单（A）

- 位置：父行下方，与标题左对齐（缩进约 68px），左侧一条 1px 竖线表示从属关系。
- 头部：`子待办` + `2/3` + 一句键盘提示（`Space 勾选 · Enter 改名`），小字 10.5px。
- 每项：
  - 18px 方形勾选框（原生 `<input type="checkbox">`，视觉隐藏、label 包一层自绘 box）→ **Tab 可达、Space 勾选**；
  - 标题按钮：点一下原地变 input；`Enter` 保存，`Esc` 取消，失焦延迟保存；空白不保存；
  - 删除按钮：hover / focus 时出现，`aria-label="删除子待办：..."`。
- 底部：`＋ 添加子待办`；点击后出现输入框，`Enter` 连续添加，`Esc` 收起；新项追加到末尾。
- 全部完成且父项未完成：底部出现轻提示（见 §4.5）。
- 父项已完成：清单仍可展开查看/修改；此时改动子项**不会**自动把父项改回未完成（需要用户显式取消父项）。
- 空清单：显示「还没有子待办」+ 添加入口。

### 4.4 抽屉（B）

- 从面板右侧滑出，宽度：宽屏 `min(86%, 340px)`；**320px 时全宽**（盖住面板，带返回/关闭）。
- 结构：
  1. 头部：`详情` + 关闭 ×（Esc / 点遮罩也能关）；
  2. 标题（只读文本，行内仍可改）；
  3. 上下文一行：日期、项目、优先级（只读 chips；避免在抽屉里再造一套编辑逻辑）；
  4. 备注：`textarea`（`min-height:100px`，`resize:vertical`，`maxlength=2000`），右上角 `123 / 2000`，**优先可见**；
  5. 子待办清单（B）或「子待办 2/3 · 在行内展开」摘要（A+B）；
  6. 底部：保存状态（`已保存` / `保存中…` / `没保存上，请重试`）+ 关闭。
- 顺序取舍：B 是「备注推荐」方案，所以备注放在清单**前面**，打开抽屉就能写；长清单在抽屉内滚动。这也暴露 B 的代价——勾子项要往下滚，A+B 因此把勾选留在行内。
- 备注保存：输入 600ms 防抖 + 失焦立即保存；写成功显示「已保存」，失败保留本地文本并显示温和提示（不把原始异常串贴进 DOM）。
- A+B 的抽屉**不重复放完整子待办编辑**，只放摘要 + 「在行内展开」按钮；避免两个入口同时维护两份状态。
- 无障碍：`role="dialog"`、`aria-modal="true"`、`aria-label="待办详情"`；打开时焦点进 textarea，关闭后回到触发按钮。焦点陷阱列为第二阶段（预览页同样不做，文档里诚实标注）。

### 4.5 完成联动（重点）

| 动作 | 默认行为 | 说明 |
| --- | --- | --- |
| 勾父项（未完成 → 完成） | **级联勾上所有子项**，播完成动效，动效播完再收起清单 | 父项完成意味着清单整体结束；不级联会留下「父项完成但子项没勾」的怪状态 |
| 取消父项（完成 → 未完成） | **只取消父项**，子项保持原状 | 用户可能只是手滑；把子项一起取消会丢进度 |
| 勾完最后一个子项 | **父项不自动完成**；底部出现一次轻提示 `全部完成，要勾掉这条吗？` [勾掉] [先不] | 自动完成会改变分组/排序/统计，属于「替用户做决定」；提示把决定权交回 |
| 点提示里的「勾掉」 | 走上面的父项完成（级联 + 动效） | 与直接勾父项同一条路径 |
| 点「先不」 | 本次不再提示；直到清单从「全完成」变回「未全完成」再重置 | 不唠叨 |
| 已完成父项里取消一个子项 | 父项保持完成；进度 chip 变成 `2/3`，可点开查看 | 不自动「重开」父项；用户要重开就显式取消父项 |

**自动完成 + 可撤销** 的对比：少一次点击，但会产生「我只是勾了最后一步，任务怎么自己归档了」的意外；撤销 toast 又要新增全局 UI 与超时逻辑，且撤销窗口过后无法恢复。**推荐「不自动 + 轻提示」**，成本最低、动机最清楚。

**动效与收起**：父项完成时，清单**不立刻消失**——先跟着父行一起播完约 1.23s 的动效（勾选框呼吸 + 对勾 + 整行淡出），再收起/随刷新归入「已完成」分组。实现上只需在 `CELEBRATE_MS` 之后再清 `open` 状态；`prefers-reduced-motion` 时跳过动画、立即收起。

### 4.6 键盘与无障碍

- 进度 chip 是 `<button>`：Tab 可达，Enter/Space 展开/收起；`aria-expanded` + `aria-controls="<子清单 id>"`；`aria-label` 带 `2/3`。
- 子项勾选框用**原生 checkbox**（不要用 `<div>` 模拟），Space 切换；label 文本或 `aria-label` 说明「勾选子待办：汇总三条争议」。
- 子清单 `role="list"`，每项 `role="listitem"`；清单容器有 `aria-label`（父标题）。
- 改名输入有 `aria-label="子待办标题"`；删除按钮有具体 `aria-label`。
- 进度变化通过 `aria-live="polite"` 的视觉隐藏文本播报（`子待办 2/3`），避免每次勾选都打断。
- 抽屉：打开聚焦 textarea、Esc 关闭、关闭回焦触发按钮；完整焦点陷阱列为第二阶段。
- 触屏没有 hover：`@media (hover: none)` 下把「＋子待办 / 备注」入口常显为淡色，避免功能不可达。

### 4.7 320 / 420 / 600 三档

- **600px**：完整单行；标题、chip、进度、备注图标、操作都在一行；抽屉 340px。
- **420px**：多数行仍单行；长标题触发换行，小字组落到第二行右对齐；抽屉约 361px。
- **320px**：标题被挤时走 `--wrap`；进度 chip 与项目在第二行；行尾操作仍在第一行；抽屉全宽；行内清单缩进后约 230px，子项标题单行省略。
- 新增零件不改变现有断点逻辑：仍然只由「标题是否被截断」决定换行，不再加一套宽度媒体查询。

## 5. 兼容、迁移、上限与错误

### 5.1 老数据 / 老客户端

- **老数据**：没有 `subtasks` → `[]`；没有 `notes` → `''`。`repairRecord` 补齐，`repairStoreDocument` 复用同一逻辑。
- **老客户端**：新字段是**追加**的，老面板的编辑提交只发改动过的字段（`patch` 语义），不会把 `subtasks` 整条抹掉；`updateOrder` 只 patch `order`。唯一风险是「第三方代码整条 put 旧对象」，本仓库内不存在这条路径。
- **不升 schema 版本**：`repairStoreDocument` 的 `version` 仍是 1；新字段缺省即可读。不需要迁移脚本。
- **旧版读新版**：旧版不认识 `subtasks`，会忽略；编辑标题/日期只 patch 自己认识的字段，不会丢子待办。可接受。

### 5.2 `repairRecord` 的兜底策略

| 坏数据 | 修复 |
| --- | --- |
| `subtasks` 不是数组 / 是 `null` / 缺失 | `[]` |
| 数组里有非对象项 | 丢弃该项，不丢整条记录 |
| 缺 `id` | 生成 `st-recovered-<index+1>`，与已有 id 冲突时加 `-1`、`-2` 后缀 |
| 重复 `id` | 保留第一个，后续重命名（同上前缀） |
| `title` 不是字符串 / trim 后为空 | 丢弃该项 |
| `title` 超 200 | 截断到 200（读盘宽容；写入仍报错） |
| `done` 不是 `true` | 视为 `false` |
| `order` 非法 | 用数组下标 |
| 超过 50 条 | 保留前 50 条（按 `order`/数组顺序），其余丢弃；不丢整条记录 |
| `notes` 不是字符串 | `''` |
| `notes` 超 2000 | **不截断**（避免静默丢用户文字）；UI 显示超限提示，保存时要求删减 |

> 读盘「宽容」、写入「严格」：磁盘上的东西可能来自手改/旧版本，不能让整条记录打不开；新写入必须满足契约，错误要能回到发起方。

### 5.3 写入校验与错误码

新增/扩展的 `WorkTodoError`（HTTP 200 + `{ok:false, reason, message}`，沿用现有约定）：

| code | 触发 | 文案建议（zh） |
| --- | --- | --- |
| `bad-subtasks` | `subtasks` 不是数组（`null` 视为清空，不算错） | 子待办必须是列表 |
| `subtasks-too-many` | 超过 50 条 | 子待办最多 50 条 |
| `bad-subtask` | 某项不是对象 | 子待办格式不对 |
| `bad-subtask-id` | id 缺失/空/超长/重复 | 子待办 id 不合法或重复 |
| `empty-subtask-title` | 标题 trim 后为空 | 子待办标题不能为空 |
| `subtask-title-too-long` | 标题 > 200 字 | 子待办标题过长（上限 200 字） |
| `bad-subtask-done` | `done` 不是布尔 | 完成状态必须是 true/false |
| `bad-subtask-order` | `order` 不是有限整数 | 子待办顺序不合法 |
| `bad-notes` | 已有 | 备注必须是文本 |
| `notes-too-long` | 已有 | 备注过长（上限 2000 字） |

- 批量写入时**整批失败**，不做部分成功，避免 UI 本地状态与磁盘不一致。
- 客户端对 50/2000 先做本地拦截（禁用添加、`maxlength`），服务端仍必须校验（工具/手改路径）。
- 错误信息只进 `role="status"` 文本节点，不拼 `innerHTML`，不把 `HTTP 500` / 原始异常串贴到行内。

### 5.4 统计 / 搜索 / 导出

- **统计**：父项算一条；子项不算；备注不算。`0/3` 的父项仍是 1 条 open。
- **搜索**：标题 + 备注（现有）+ 子待办标题（建议新增，见 §3.4）。命中的是父项，返回父项。
- **导出**：当前没有独立导出路由；JSON 存储/备份天然包含 `notes` 与 `subtasks`。若未来加「导出 Markdown/文本」，子项渲染成复选框列表、备注放在父项下；统计列仍按父项计。
- **排序/分组**：只看父项的 `due` / `priority` / `project`；子项不参与。

### 6.4 风险清单

1. **320px 横向空间**：新增进度 chip + 备注图标会让标题更早换行；靠现有 `--wrap` 兜底，但需要在真机量一次。

3. **并发覆盖**：整数组 patch 是 last-write-wins；单用户可接受，多窗口/agent 同时改需第二阶段原子 op。
4. **焦点管理**：清单内改名/删除/抽屉开关要避免焦点丢失；用稳定 `data-*` key 恢复。
5. **备注长度**：2000 是现有契约；若用户要更长，先拍板上限再动常量，避免 UI 与工具描述不一致。
6. **触屏**：没有 hover，入口必须常显或放进抽屉，不能只依赖鼠标。
