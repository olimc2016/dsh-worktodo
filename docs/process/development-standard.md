## 0. 一页速查（只列动作，细则看后面）

### 改动前

- [ ] 先跑全量自检，确认基线**是绿的**，并且**显式看退出码**：`npm test; echo "exit=$?"`（不要用 `| tail` 看结果，管道返回的是 `tail` 的退出码）
- [ ] 确认构建工具链可用：构建失败必须硬失败；产物没更新 = 后面的烟测在测旧代码
- [ ] 改宿主半侧 → 必须**重启 DSH** 才生效；只改客户端 → 必须重新构建并提交产物
- [ ] 插件「装完起不来」/ 宿主启动失败 → 先查 profile 里有没有**第二份平台包**（§2.7、§6.5）
- [ ] 改安装 / 升级 / 更新路径 → 先读 §2.12–§2.14 与 §4.4；**安装路径不许跑包管理器**
- [ ] 多 agent / 多会话并行 → 先声明**写域**，同一文件同一时间只有一个写者（§3.2.13）

### 提交前

- [ ] **双环境**（本机 + 干净环境）都全绿，且每一套都有 `exit=0` 的证据（§3.2.6）
- [ ] 新增 / 修改判定逻辑 → 做一次**反向验证**（故意破坏，确认变红，记下哪条用例红）
- [ ] 产物与源码**同一提交**；`git status` 只含自己写域内的改动
- [ ] 动了文档 / 命令 → 文档门禁绿：引用的路径与脚本必须真实存在（§3.2.15）

### 发布前

- [ ] `package.json` 版本 + `CHANGELOG.md` 条目（写「用户可感知」的变化）
- [ ] 本仓发版前脚本（若有，见 annex 命令表）全绿；没有就按 §5.3 逐条跑并留退出码
- [ ] `npm pack --dry-run` **逐条看清单**：不能含 node_modules、私有文档、截图、内部审查报告、凭据（§5.8）
- [ ] 发布面断言绿：平台包只能 optional peer、`dependencies` 里没有 `@deepseek-ai/*`、顶层无静态 import

- [ ] 真机重启 + 实际数据对账一次（§4）

## 1. 结构通则

```text
<plugin>/
  package.json          # name / version / dsh.client / dsh.bundle.patch / files 白名单
  cordis.patch.yml      # 插槽行（id 必须唯一；多包名时各自不同）
  lib/
    index.js            # 宿主半侧入口：export name / inject / apply(ctx, config)
    client.js           # 浏览器半侧【构建产物，必须入库】
  src/                  # 源码：宿主共享纯逻辑、客户端源码（本仓分工见 annex）
  tools/                # 构建、自检、烟测、发布辅助（默认不进 npm 包）
  docs/                 # 设计、规格、评审、事故（不进 npm 包）
  README.md / CHANGELOG.md / LICENSE
```

**硬约定**

1. 客户端 bundle **入库**：用户从 npm / GitHub 安装时不会现场构建；CI 必须能重建出同样内容。
2. `files` 白名单显式列出（`lib`、`src`、`cordis.patch.yml`、运行时安装器（若有）、文档、LICENSE），避免打包垃圾。
3. 一个仓库只维护**一份源码**。多包名用生成器，**禁止复制分叉**。
4. `docs/`、`.github/`、`node_modules/` **不得进 npm 包**。

## 2. 开发规范

### 2.1 宿主与渲染分离

- `inject` **只写必需**服务（通常 `['webServer']`）。可选服务（`settings`、账号等）用 `ctx.inject([...], cb)` 探测，缺失时降级而不是整体加载失败。
- 取服务用 `ctx.get?.('name') ?? ctx.name` 双通道，兼容不同组合与测试桩。
- 浏览器半侧只做展示与交互；一切数据 / 写操作都经宿主的 HTTP 路由（客户端不能直接碰文件、凭据、设置）。

### 2.2 多包名（同源码不同名）

> 适用于同一份源码发布多个包名的仓库（本仓是否为多包名见 annex）。单包名仓库可跳过本节。

所有会撞车的标识**一律由包名派生**，不要让两个名字共用：

| 标识 | 派生方式 | 撞车后果 |
|---|---|---|
| 插件 `name` | 包名去 `dsh-` 前缀 | 加载器重复 |
| webServer 路由前缀 | `/${短名}` | 第二个插件 register 抛错 |
| settings 命名空间 | `/${短名}` 同源 | 配置互相覆盖 |
| 浏览器 slot id | 短名（主包可保留历史值） | 侧栏重复注册 |
| locale 命名空间 | 短名 | 词典互相覆盖 |
| cordis 插槽行 id | 写在各自 `cordis.patch.yml` | 加载器报重复行 |

> 实测：两个包同时装进一个 profile 也不冲突 —— 但前提是上表全部做到；必须有专门的测试守住。

### 2.3 数据源与口径（最容易出「用户不信」的地方）

- **单一真源**：同一份数据只有一个权威来源；回退路径必须显式标记、且不能与真源同时写（否则数据「分裂」成两份，用户看到的两处对不上）。
- **降级必须可解释**：降级要能回答「为什么降级、现在少什么、怎么恢复」，并在 `/health` / 面板给出可执行提示；不许「看起来正常但少了能力」。
- **同一张表只放同一口径的数字**：官方数据与本地推算混排 → 用户会发现「加不上」，信任瞬间归零（真实事故）。估算值必须标注「估算 / 允许几分差异」，脚注写清算式与舍入。
- **金额用十进制字符串运算**（避免 `0.1 + 0.2`），展示固定小数位；小额至少 4 位。
- 每个派生数字都要能回答：**它来自哪、怎么算的、和官方差多少是正常的**。
- 平台接口的鉴权方式、时间窗口对齐、请求头等细节**因平台而异**，属于仓库特有知识 → 写进 annex，不要凭记忆猜。

### 2.4 配置与凭据

- 设置项走 schema 校验（schemastery），`description` 写中文；默认值单点定义，schema 与代码共用。
- 凭据**只存引用**，永不写日志、永不回显、永不进仓库。
- 面板内可改设置 → 宿主提供写接口，服务端必须做：**字段白名单 + 类型 / 范围校验 + 体积上限**；写入后清缓存让下一次读立即生效。
- 设置持久化要**原子写**；非法值拒绝且不写盘；损坏时回退默认并告警。

### 2.5 UI 约定

- **同一排的卡片必须同一 surface**（同圆角、同阴影、同底色），否则视觉「不在一个平面」（真实事故）。
- 窄栏用 `flex-wrap` + `minmax(...)`，**不要**用固定网格让某一列被挤成一字一行。
- 数字：`font-variant-numeric: tabular-nums` + `white-space: nowrap`；表格 `colSpan` 时不要加固定表格布局（会折行）。
- 文案：正文一句话，解释放 `title` / tooltip；中英双语同步维护（有 i18n 的仓库）。
- 图表：柱上只留一个主标签；x 轴标签过密要抽稀。
- 交互必须有**键盘可达**与可见焦点；状态提示用文本节点，绝不用 `innerHTML`。

### 2.6 安全与隐私（硬红线）

- **公开仓库不得出现**：任何账号名 + 邮箱组合、token、`.npmrc` 内容、账号找回 / 客服沟通材料、内部绝对路径、用户会话截图。
- token 只以「临时 npmrc + `chmod 600`」形式存在于临时目录，**用完立即删除**；不得写进仓库、脚本、命令行历史。
- 账号 / 凭据类文档只放**仓库外的私有目录**，或只在对话中给出。
- 撤回公开内容要**快**：发现已推送 → 立刻本地回滚；已推送的改中性文案并评估历史清理（force-push 影响他人克隆，需先确认）。
- 隐私门禁扫的是**两个面**：npm 发布包 + git 跟踪文件。

### 2.7 宿主平台包：只能 optional peer，且不得多带一份（真实启动失败事故）

**规则（四条）**

1. `@deepseek-ai/*` 这类**宿主提供的平台包**（`dsh-tools`、`dsh-storage-domain`、`dsh-home-paths`、`cordis` 等）**只能**声明为 `peerDependencies` + `peerDependenciesMeta: { optional: true }`；**`dependencies` 里不得出现任何 `@deepseek-ai/*`**（应为空）。
2. **不得在模块顶层静态 import 平台包** → 必须在函数内**动态 import + 失败降级**。
3. 版本声明用**宽松范围**（如 `^0.2.0-rc.2`；宿主闸门按 includePrerelease 判 peer），不得写死当前运行时的精确版本（见 §2.8）。
4. 平台包缺失 / 版本不符时**只允许降级本插件**（工具不注册、回退存储），**绝不连累宿主启动**（见 §2.10）。

**机制：一份硬依赖如何拖垮整个宿主（事故链）**

profile 的 `nodeLinker=hoisted`：

1. **任何硬依赖都会被摊平进 profile 顶层** ✗ —— 插件声明 `dependencies`，pnpm 就把平台包装成 `profile/node_modules/@deepseek-ai/*`（而且可能解析到旧版）。
2. **profile 层解析优先于宿主安装层** ✗ —— 从 profile 发出的 bare import 先命中本层副本，宿主自带的那份被绕过。
3. **宿主有兼容性闸门** ✗ —— app 升级后，profile 里的旧版 core 包被判 incompatible，**整行被 disable**。
4. **被 disable 的行不出现在 pending 名单里** ✗ —— 服务提供者凭空消失，下游全部等待：

```text
startup failed: 1 required plugin did not activate

Plugins waiting for services (14):
  agent-loop (required)      tools
  workspace                  storageDomain
  …

dsh: disabling profile plugin row "tools":
  … is incompatible with dsh <宿主版本> …
```

**crash 日志里既没有 `Failed plugins` 段、也没有 disable 行**，所以从用户能拿到的日志**看不出真因**；排查要走宿主 stderr（§6.5）。诊断自解释是插件侧义务（§2.11）。

**自动防线（发布阻断）**：发布面断言脚本必须校验——
① `dependencies` 无 `@deepseek-ai/*`；② **所有** `@deepseek-ai/*` peer 标了 optional；③ 宿主半侧源码顶层无静态 bare import；④ 运行期动态 import 的 bare 包集合 == peer 声明；⑤ 脚本自带**反向自检**（把包装回 `dependencies`、或去掉 optional，校验器必须报错）。`prepublishOnly` / 全量自检 / CI 都会跑 —— **违反即发不出去**。

**静态断言证明不了「装出来只有一份」**：必须再做一次 §4.1 的 profile 模拟（插件目录内无平台包副本、解析到顶层宿主那份）。

### 2.8 宿主版本对齐（升级模拟是发版前置，不是可选项）

- **插件不得写死宿主包版本**：`peerDependencies` 用能覆盖未来补丁 / 预发布的宽松范围；`devDependencies` 的精确版本只是**测试夹具**，不随发布包出去。
- **宿主升级 = 插件的回归事件**：升级会同时改变平台包版本、profile 解析与兼容性闸门。插件「一行没改」也可能装坏宿主。
- 因此：**宿主大版本升级后，必须重做 §4.1 + §4.2 再发版**，并在 `CHANGELOG.md` 写明「已对 DSH x.y 验证」。
- 不得在运行时「顺手」安装 / 升级平台包：profile 属于用户与宿主，插件写它就是越权（§2.12）。

### 2.9 启动期纪律（`apply` 是宿主启动路径上的代码）

- **apply 不阻塞**：不 `await` 网络、子进程、大文件、profile 读写；目标 <50ms，任何可能慢的 IO 都要有上限。
- **网络 / 子进程 / 写盘延迟且可取消**：定时器登记进生命周期并 `unref()`；fetch 用 `AbortController`；插件卸载 / 重载即取消。
- **任何「自动修改用户环境」的动作默认关闭**，或必须用户显式开启；默认值要能一句话说清。
- 每个 `void promise` / `.then()` 必须有 `.catch` —— 宿主进程里 unhandled rejection 就是一次未捕获异常。
- 启动期不读热路径上的 profile / `node_modules` 清单：面板轮询会把开销放大。

### 2.10 错误不连累宿主（只降级本插件）

- 平台包缺失、存储打不开、工具注册失败、路由重复 → **只降级本插件**，`apply()` 正常返回而不抛。
- 降级必须**显式可查**（状态字段 + `/health` 带原因），不许「看起来正常但少了能力」。
- ESM 不允许 `try { import } catch` 包住静态 import —— 所以**只能**在函数内动态 import（发布面断言直接扫源码）。
- 已知边界：插件模块本身语法错 / JSON 坏，插件侧兜不住 → 靠「加载真产物」与 §4.1 的 profile 模拟拦在发布前。

### 2.11 可观测性（关键动作不能只写日志）

- 升级、迁移、存储切换这类**改变用户环境或数据位置**的动作，必须有**可查的状态与诊断**：状态文件（原子写）+ HTTP 诊断接口 + `/health`。
- **不要把关键信息只写进会被丢弃的日志**：崩溃日志可能只留一行 `StartupError.message`，把真正原因丢掉。诊断要能**离开日志独立存活**。
- 诊断进面板时只用文本节点；日志尾部限长（数行），不写凭据、不写业务内容。
- 状态要能跨重启讲清「上次做到哪一步、为什么失败」（`failedOperation` / `attemptedSteps` / `reason`）。

### 2.12 安装 / 升级：写用户环境必须是事务，且离运行态

**两条铁律**

1. **绝不对 live profile 跑包管理器** ✗ —— 运行期（宿主进程内，或由宿主拉起、会写同一个 profile 依赖树的任何进程）不得执行 `pnpm add/update/install`、`npm install`、`dsh plugin add` 这类会重写 `node_modules` 的命令。pnpm 会重写整个 `node_modules`，正在运行的 DSH 也在同一个目录里解析模块 —— 窗口期内模块被替换 / 裁剪 → **点安装后黑屏**。放后台跑包管理器**不能**消除这个窗口。
2. **首选形态只有一种** ✓：**下载 → 解包 / 校验 → detached 独立安装器 → 只原子替换本插件目录 → 提示重启**。
   - 安装器是**单文件**，只 import `node:` 内置模块（半更新状态也能独立跑）；
   - 只替换本插件目录（pnpm 下是它 `realpath` 指向的真实目录）；
   - 幂等：目标已是目标版本 → 直接成功，一个文件都不动；
   - 顺序：copy 新目录到**同级**临时目录 → 旧目录 rename 成备份 → 新目录 rename 成目标 → 读 `package.json` 校验**落盘版本**；
   - **不写** profile 的 `package.json` / lockfile，**不碰** `node_modules` 里别人的目录。

**如果某条路径确实要写 profile 的清单 / lockfile / `node_modules`（历史路径或应急），必须**：

- **原子**：临时文件 + `fsync` + `rename`；win32 回退**不得先删目标** —— 先落 `.bak`、再删、再 rename；恢复不了就保留 `.bak` 并把路径写进错误。
- **快照**：`package.json` 与 lockfile 属**同一事务**，逐字节快照与还原；本次新建的文件要删掉。
- **锁**：`open(..., 'wx')` 原子建锁，内容带 pid / host / at / token；拿不到即 `busy`，**不重试**；stale 只回收一次；只删自己 token 的锁。
- **不手写 profile 的 JSON**：能走宿主 CLI 就走；CLI 明确拒绝必须 **failed 并停止序列**，**绝不降级到 pnpm** 绕过宿主保护。
- **profile 定位只从模块自身路径推**：取**最后一个** `node_modules/<包名>` 段；推不出就**零写盘失败**，绝不按「第一个匹配」指到外层 profile。
- **杀进程要杀整棵树**：POSIX 进程组 / Windows `taskkill /T /F`；超时后连 stdout / stderr 一起 destroy。
- **卸载后零写盘、零子进程**：`disposed` 在每个异步收口前检查；卸载后连回滚也不写。
- **「成功」只认落盘版本变了**，不认退出码（实测出现过退出码 0 但 `added 0`）；失败诊断固定字段（step / argv / exitCode / logTail / target / versions …）。
- Windows `rename` 遇 `EPERM` / `EACCES` / `EBUSY` / `ENOTEMPTY` 做指数退避重试；仍失败则回滚并如实报错，**绝不**先删目标再「重试」。

**验收**：安装 / 升级类改动必须过 §4.4 五项（其它文件逐字节不变 / 零包管理器 / detached 证据 / UI 不阻塞 / 失败回滚）。

### 2.13 本地 / 开发安装是一等状态

- `link:` / `file:` / `workspace:` / symlink 指向 profile 外 / 推不出 profile → **`unsupported` 温和态，不是错误**。
- 判定必须在**下载、加锁、起子进程之前**（只读预判）；状态映射回 `idle`，`failure` / `failedOperation` 为 `null`，`reason` 是稳定种类（如 `link-install` / `profile-undetermined`）。
- 面板：muted 色、无 action、无重试按钮、不显示原始异常串；技术细节只进诊断；文案必须**可执行**（「本地链接安装（开发模式），请用 git / pnpm 工作流更新」）。
- **不要误伤正常安装**：包管理器内部 symlink 目标在 profile 的 `node_modules` 内，不算开发安装（要有反误判用例钉住）。
- **不许猜 profile**：推不出就零写盘失败，绝不按 `$DSH_HOME/profiles/*` 或 `process.argv` 猜一个。

### 2.14 后台动作分档：默认必须最保守

**三档语义**

| 档 | 面板文案 | 后台行为 | 网络 | 自动下载 / 安装 |
|---|---|---|---|---|
| `off` | 禁用更新 | 完全不检查（启动检查、轮询、手动检查都不打网络） | **零请求** | 否 |
| `manual`（**默认**） | 仅提示新版本 | 只检查（超时 + 有限重试 + 退避）；有新版本只提示 | 检查时才请求 | **绝不**；用户点「下载」「安装并重启」才动 |
| `auto` | 自动更新 | 检查 → 自动下载 → 自动安装；装好停在 `installed` + `restartRequired` | 检查 + 下载 | 是；**但不自动重启** |

**规则**

1. **默认必须最保守**：用户没表态时 = `manual`（只提示）。
2. **关闭 = 零网络**：`off` 下启动检查、轮询、手动检查都不许发请求（用本地假 registry 记账断言 0 请求）；切到 `off` 时 abort 在飞检查，晚到的结果按 epoch 丢弃。
3. **失败不得吓人**：网络 / 超时 → 温和 `check-failed`（muted、无 action、不显示原始错误串）；原始异常只进诊断；自动退避重试，成功即复位。
4. **档位只决定「谁触发」，不改变事务**：`manual` / `auto` 共用同一套下载护栏、锁、detached 安装器、失败回滚；`auto` 在下载完成后要**再确认一次档位仍是 `auto`**。
5. **不自动重启**：`restartRequired` 只渲染一条提示（`role="status"`、纯文本、没有「重启」按钮），重启永远由用户做。

## 3. 测试规范

### 3.1 分层（每层职责单一）

| 层 | 职责 | 要求 |
|---|---|---|
| 纯逻辑回归 | 聚合、去重、解析、计价、状态机 | 不依赖个人路径；找不到数据**跳过**而不是失败 |
| 宿主烟测 | 路由、设置、数据取数、工具、自升级、跨平台模拟 | **假 ctx**，网络一律打桩，不允许真出网 |
| 客户端烟测 | bundle 能注册、标识派生一致、首屏、错误边界、**真渲染一次** | 桩 React / 迷你渲染器，无浏览器 |
| 契约测试 | 客户端请求的路径 / 字段 ↔ 宿主真的消费 | 静态提取 + 端到端报文，防「字段名打错静默失效」 |
| 元测试 | 版本字面量、依赖面、import 形态 | **扫源码全文**，不用位置白名单；自带边界自测 |
| 发布面 | 隐私、打包白名单、收录条目 | 两个面都查：npm 发布包 + git 跟踪文件 |
| 文档 | 文档引用的路径 / 命令 / 脚本真实存在；跨仓共享正文同步 | 纯静态，可在任何环境跑 |

> 本仓实际 suite 名、数量与全量自检步数见 annex。

### 3.2 铁律（血泪教训）

1. **测试必须跑「刚构建的产物」**。
   事故：构建工具软链悬空 → 构建**静默失败**，烟测加载的是**旧** bundle → 全绿，但测的是上一版代码。
   规范：构建失败必须**非零退出**；`npm test` 的第一步应构建并校验产物新鲜度；「改完代码结果一模一样」先怀疑构建。

2. **反向验证（mutation check）**：新增或修改判定逻辑后，**故意破坏一次**，确认测试 FAIL，再恢复；并**记下是哪条用例红的**。
   没有通过反向验证的测试**不许入库** —— 假测试比没测试更危险。真实案例：一个假渲染测试把 bug 塞回去仍然 PASS → 已撤。

3. **断言「会撞车的事实」**，不要断言实现细节：行 id、路由前缀、命名空间、slot id、窗口对齐、口径一致、金额自洽。

4. **回归样例要能离开这台机器跑**：禁止硬编码家目录绝对路径；用 fixture / 环境变量，缺失则跳过。

5. **网络全部打桩**：烟测里出现真实 fetch 就是缺陷（偶发失败、泄露 token、拖慢 CI）。

6. **双环境门禁 + 显式退出码**。
   本机一套、干净环境一套（`env -i`、不继承宿主相关环境变量、`CI=true`），**两套都要全绿且退出码 0**。
   关键在**显式检查**：`node tools/x.mjs | tail -20` 的 `$?` 是 `tail` 的，基线失败会被整段吞掉；只认 `...; echo "exit=$?"` 或 `set -o pipefail`。

7. **防回归元测试**（事故产物，必须留着）：
   - **「源码里不得残留当前版本号字面量」**：从 `package.json` 派生版本常量，再扫**源码全文**找孤立字面量（边界正则 `(?<![\d.])<ver>(?![\d.])`），命中报行号；注释也会被扫（所以注释里不许写版本字面量）。
   - **「依赖面不得出现 `@deepseek-ai/*` 硬依赖」**：并带**反向自检** —— 把包塞回 `dependencies`、或去掉 optional，校验器必须报错。
   - 元测试要**扫全文**：只盯已知位置或白名单必然还会漏。

8. **CI 与本地必须一致；「本地碰巧绿」也是缺陷**。
   ESM 静态 import 会在模块体之前求值：测试文件顶部写 `process.env.X='1'` 再静态 import 被测模块，**模块求值时就看不到它**。
   - 环境变量 / 开关一律**调用时读**；
   - 测试开关由**父进程 spawn 前**注入；
   - 专门造一条**时序用例**（慢 registry）证明「检查在飞时行为仍正确」。

9. **跨平台要有模拟测试**，不能只靠「代码里写了 win32 分支」：路径（盘符 / 反斜杠 / `%20` / UNC）、执行器、`rename` 三态、进程树（真起孙进程，超时后必须死）。平台用测试缝注入，不改真实 fs 语义。

10. **客户端要有「真渲染」路径的测试**。
    假渲染到不了渲染分支，会漏掉「黑屏」类 bug。最低要求：把面板树**真渲染一遍**（函数组件真调用、类组件 `render`、错误边界按 React 语义走），并至少覆盖一次「有数据」的完整面板。

11. **门禁红了绝不 commit / tag / 发布，而且必须显式检查退出码**。
    - 只认 `...; echo "exit=$?"` 的结果；**`| tail` / `| grep` 的输出不算证据**；
    - 「本地碰巧绿」「CI 绿但本地红」都不算绿：**双环境都全绿且 EXIT=0** 才允许 commit / tag / 发布；
    - 门禁红了先修红（或写清为什么这条红可以忽略并留证据），不许「先提交再说」。

12. **元测试必须自带边界自测**（扫描器自己也会错）：
    - 数字边界：`0.2.1` 与 `0.2.10` 是前缀关系，必须用边界正则，并有**样本自测**证明二者不互相误伤；
    - **注释也会被扫描**：这是刻意设计，所以注释里不许写版本 / 敏感字面量；
    - 元测试报错必须带**行号**。

13. **同一文件同一时间只允许一个写者**（多 agent / 多会话并行）。
    先**声明写域**，再动手；写域重叠就串行，不许「各改一半再合」。
    - 在别人写的同时跑门禁，结论**不可信**（读到半写文件 → 假红；互相覆盖 → 假绿）；
    - 报告里记录 `git status` 快照与被审文件的哈希，结论只对那个状态负责。

14. **推送 / 网络失败要做后台重试到成功，不要手工反复**。
    可重试：`git push` 的 `Empty reply` / HTTP2 framing、registry 抖动 → 用 HTTP/1.1 + 有限次退避，**后台重试到成功**并留最后一次日志。
    不可重试：权限 / 认证 / 拒绝 → 立刻停，别重试。

15. **文档引用也是代码，必须可验证**。
    文档里出现的仓库路径、脚本、命令、脚本名必须真实存在；跨仓共享正文必须逐字节一致。
    做法：文档门禁静态扫描（引用存在性 + 共享段比较），纳入全量自检；**引用一段没实现的工具 = 下一轮审计的假红线**，写进文档前先让它存在。

### 3.3 已知缺口（写清，不许假装已拦住）

- **真 React + DOM 挂载仍未落地**：迷你渲染器覆盖「渲染期抛错 / 错误边界」，但不覆盖 `setState` 重渲染、并发渲染、浏览器 API 差异。
  验收：故意去掉关键参数或改坏 `setState` 分支时，该测试必须 FAIL。
- **profile 模拟 / 宿主升级模拟仍是手工**：没有一条命令能给出四条断言；发版前按 §4.1 / §4.2 做，并由发版前脚本打印人工清单提醒。
- **CI 跨平台不完整**：主 job 只跑一个 OS；Windows 目前只有观测 job（允许失败），转正条件是全套 suite 在 Windows 连续绿 N 次。
- **没有真机 Windows**：`rename` 覆盖、`taskkill /T /F`、杀软 / 索引器占用导致的二次失败都只是模拟。
- **「环境变量提升」类缺陷只能靠约定 + 一条时序用例**，没有静态检查能证明「所有开关都在调用时读」。
- **并发写没有自动闸门**：两个进程写同一文件拦不住，只能靠写域声明 + 串行 + `git status` / 哈希留痕。
- **发布流水线还有人工项**：绑定页 Allowed actions 只能在 npm 网页核对；「暂存区只批最新」没有机械检查。
- **旧安装事务用例退场**：若将来重新引入「写 profile 清单 / lockfile」的路径，对应的同事务回滚用例必须恢复。
- **防线状态表仍是人写的**：✅ / ⚠️ / ❌ 与脚本改名不会自动联动；文档门禁只能保证「引用的脚本存在」，保证不了「状态标注正确」。

### 3.4 跨平台

- CI 矩阵（哪些 OS / Node 版本）见 annex；矩阵变更要同步 annex。
- 不要依赖系统 `PATH`：DSH 桌面端进程的 PATH 很短；调用 CLI 用包内入口 + 捆绑 node。
- 平台差异（macOS `Contents/Resources/app.asar`、Windows `resources/app.asar`）要有单元用例覆盖。
- **Windows 上不要 shell 猜路径**：优先 `node + 脚本`（argv 数组、无 shell）；只有找不到时才用 `.cmd` + `shell: true`，并把每个参数逐字加引号。
- **杀进程树**是两套实现（POSIX 进程组 / `taskkill /T /F`），两边都要有「孙进程必须死」的可执行用例。

## 4. 验证规范（发版前必须做的）

> 前 3 项是**硬门禁**（全过才允许进 §5），其余是发版前必做的验证。**任何一项没有「退出码 0」的证据，都算没过。**

1. **双环境全绿，且显式退出码**：本机 + 干净环境（不继承宿主相关环境变量、`HOME` 指向临时目录、`CI=true`），两套都全绿。
2. **产物与源码一致**：重新构建后 `git status` 无差异（证明入库产物可重建）。
3. **发布面断言绿**：平台包 / 依赖面 / 顶层 import 形态；发布包白名单逐条看过。
4. **profile 模拟安装**（§4.1）：证明「装出来只有一份平台包，且解析到宿主那份」。
5. **宿主升级模拟**（§4.2）：宿主刚升过大版本时**必做**。
6. **双端验证**：版式预览（若有工具）+ **真机**：完全退出 DSH 再启动 → 打开面板 → 核对数据。
7. **数据对账**（不能只看「有数」）：同一口径下的合计 / 明细 / 多窗口互相自洽；具体对账项见 annex。
8. **长跑 / 多窗口 / 大数据**（§4.3）。
9. **异常路径验证**：断网、未登录、无凭据、只有本地数据、凭据过期、平台包缺失、存储打不开 → 面板必须给出可执行提示，不能白屏 / 空转。
10. **回归截图存档**：每次发布留一张真机截图（存私有目录，不入公开仓库）。
11. **安装 / 升级类改动 → 再做 §4.4 五项**（其它文件逐字节不变 / 零包管理器 / detached 证据 / UI 不阻塞 / 失败回滚）。缺一项都不算验过。

### 4.1 profile 模拟安装（平台包事故的验收动作）

目标**不是「能装上」**，而是**装出来只有一份平台包，且解析到宿主那份**。静态断言（§2.7）只能证明清单 / import 形态对，证明不了装出来的形状。

```bash
# 0) 打真实 tarball（用本仓的包管理器）
# 1) 假 profile（两层，与 DSH 的 installation/profile 解析同形）：
#    <sim>/profiles/{package.json, node_modules/@deepseek-ai/…}   ← 顶层 = 宿主安装层替身
#    <sim>/profiles/desktop/package.json                          ← 只依赖上面那个 tarball
# 2) 在 desktop 层装 tarball
```

四条断言（全过才算过）：

- [ ] `profiles/desktop/node_modules` 顶层**只有本插件**，没有 `@deepseek-ai/*`
- [ ] 插件目录内**不存在** `node_modules/@deepseek-ai`（hoisted 会摊到 profile 顶层，这条查「插件自带副本」）
- [ ] 从插件入口解析平台包 → 落在 `profiles/node_modules/@deepseek-ai/*`（宿主层），版本 = 宿主版本
- [ ] **反向样本**：把平台包塞回 `dependencies` 再 pack 装一遍 → 第 1、3 条必须变红（第 2 条两种形态都可能成立，不能只靠它判别）

> 现状：仍是**手工**（发版前脚本只打印这条清单）。自动化是下一版该补的缺口（§3.3）。

### 4.2 宿主升级模拟

1. 假 profile 里先装**旧版**平台包 + 本插件 → 能启动；
2. 把顶层平台包换成**新版**（等价于 app 自动更新），profile 里的插件不动；
3. 启动并看诊断。

断言：

- 不出现 `disabling profile plugin row …`、`Plugins waiting for services`、`1 required plugin did not activate`；
- 插件 `/health` 里工具 / 官方存储是「可用」还是「已降级」，降级原因必须可读；
- 面板能打开、能读数据。

> 跨版本最容易在**预发布号**上出事：真正的风险是**副本抢先解析**，不是 peer 范围。核心是 §4.1 的「只有一份」。

### 4.3 长跑 / 多窗口 / 大数据

- **`apply → dispose` 10 轮**：进程 / 句柄 / 定时器 / 子进程**零增长**；卸载后零写盘、零 spawn。
- **多窗口**：两个面板同时开；轮询在后台标签页要停。
- **大数据**：最大规模数据下读接口的字节数与渲染耗时；内存 / 收敛后的形状不得回退成多份；单文件写入上限（如 32MiB）。
- **泄漏**：动效定时器、窗口监听、`setInterval` 卸载时全部清掉。
- **并发**：两个实例 / 两个进程同时触发写操作 → 锁必须让其中一个 `busy`，且它零写盘。

### 4.4 安装类改动的验收

> 适用：任何「会改用户环境」的改动 —— 安装 / 升级 / 回滚 / 原子写 / 锁 / 进程树 / 卸载清理。**五项全过才算过。**

- [ ] **① 其它文件逐字节不变**：对 profile 做逐文件快照（内容按字节、权限位、符号链接目标），安装前后深比较；断言除本插件目录外零差异，`package.json` / lockfile 逐字节不变。只看「版本变了」不算证据。
- [ ] **② 零包管理器**：安装路径不许出现包管理器命令。用**绊线 bin**（PATH 上放会记账的假命令）断言调用数为 0，而不是靠人读代码。
- [ ] **③ detached 证据**：纯函数断言 spawn 规格是 `detached: true` + `stdio: 'ignore'` + `unref()`；端到端：注入安装器延迟后，宿主 POST 安装**立即返回** `installing`；宿主 dispose 后安装器**继续跑完**。
- [ ] **④ UI 不阻塞**：`startInstall` 返回 <500ms（断言）；首屏在安装进行中仍 <100ms。
- [ ] **⑤ 失败回滚**：注入失败 → 目标目录逐字节恢复旧版本、状态 `failed` + 原因、备份可用、日志尾部进诊断。反向：把回滚分支改成恒不执行，测试必须红。

### 4.5 验证记录（留痕）

- 每条反向验证记：**破坏了什么、哪条用例变红、恢复后是否复绿**。
- 真机验证记：重启后截图 / 对账结论（存私有目录）。
- 发版前脚本的输出（退出码 + 汇总）贴进发版记录。

## 5. 发布规范

### 5.1 版本与提交

- 语义化版本；`package.json` 与 `CHANGELOG.md` 同一次提交更新。
- **tag 与 npm 产物必须是同一 commit**（先 bump → 提交 → tag → 发布，避免 tag 指旧代码）。
- 提交信息写「为什么改」，不写「改了啥」；前缀沿用仓库现有习惯（如 `feat:` / `fix:` / `docs:` / `release:`）。

### 5.2 npm 发布方式（优先级从高到低）

1. **Trusted Publisher（OIDC，推荐）**
   - 绑定：包页 → Trusted Publisher → GitHub Actions → `<org-or-user>` / `<repo>` / `<workflow 文件名>` / Environment 留空。
   - **跨账号可绑**：包属于 npm 账号 A、仓库属于 GitHub 账号 B 完全合法（绑的是「仓库 + 工作流」）。
   - 工作流：`id-token: write` + `--provenance --access public`，全程无 token。
2. **临时 token（次选，仅应急）**
   - 临时 npmrc：`chmod 600`，用 `NPM_CONFIG_USERCONFIG` 指向它；指定官方源。
   - **发布后立即删除临时 npmrc，并撤销该 token**（尤其 token 曾出现在聊天 / 日志里时）。

### 5.3 发布前硬门禁（缺一不发）

```bash
# ① 本机全量自检（含构建），显式看退出码
npm test; echo "exit=$?"
# ② 干净环境再跑一套
env -i HOME=/tmp/cihome PATH="$(dirname "$NODE"):/usr/bin:/bin:/usr/sbin:/sbin" CI=true \
  npm test; echo "exit=$?"
# ③ 发布面断言（本仓脚本与命令见 annex）：平台包 / 依赖面 / import 形态 / 运行时安装器在包里
# ④ 打包白名单
npm pack --dry-run
```

- **①② 必须都全绿且退出码 0**；**③** 覆盖依赖面与 import 形态；**④** 逐条看清单。
- **⑤ profile 模拟安装**（§4.1）四条断言全过；宿主刚升级过 → 加做 §4.2。
- 产物与源码同一 commit（客户端 bundle 必须真的在 tarball 里）。

### 5.4 暂存 ≠ 发布（staged publish）

- 暂存发布只把版本推进**暂存区**，`latest` **不动**；必须维护者在网页上 **Approve**（2FA / WebAuthn）才真正上线。
- **批准前必须完成 §4 全部验证**：暂存区不是「先占位、后补验证」的地方。
- **批准是人做的事**：不要在 CI 里自动批准、也不要用 token 绕过 2FA。
- 实测副作用：暂存发布**不写 registry 的 `readme` 字段**（包页面会没有 README，tarball 里是齐的）。要页面 README 就走直接发布，或发布后补查。

### 5.5 发布后核验

```bash
npm view <pkg> dist-tags versions --registry=https://registry.npmjs.org/
npm view <pkg>@<ver> version dependencies peerDependencies
```

- `latest` 指向新版本、版本号正确、`repository` / `description` 正常、tarball 内含宿主入口与客户端 bundle。
- **从 npm 真装一次**（不是装本地 tarball）：临时 profile / 目录里装 `<pkg>@<ver>`，确认 ① 装出来的 `dependencies` 为空（无 `@deepseek-ai/*`）；② 插件目录内无 `node_modules/@deepseek-ai`；③ 平台包解析到顶层宿主那份。
- 任何一项不对 → 立刻按 §5.6 止血，别等用户报障。

### 5.6 坏版本处置（止血顺序不能反）

1. **先 `npm dist-tag add <pkg>@<good> latest`** —— 用户的自动更新（唯一依据是 `latest`）立刻停止拿到坏版本；
2. 再决定撤版本还是发补丁。

| 时机 | 动作 | 说明 |
|---|---|---|
| 发布后 **72 小时内** | `npm unpublish <pkg>@<ver>` | npm 允许的撤回窗口；同一版本号**不可重发**，撤了必须换版本号 |
| 超过 72 小时 / 已传播 | `npm deprecate "<pkg>@<range>" "原因 + 替代版本"` | 装上的人会看到警告；同时尽快发补丁版 |
| 任意时刻 | `npm dist-tag add <pkg>@<good> latest` | 止血第一步，先做 |

- **只撤单个版本**，不要 `unpublish` 整个包。
- **`latest` 是自动更新的唯一依据**：只改 `latest` 也能立刻止住扩散；反之只发版本不动 `latest`，老用户永远收不到。
- 事后必须写一篇复盘（症状、根因、防线、还差什么）并进事故索引。

**包名所属账号不可用时**：用可控账号下的**新包名**继续发布（同源码，生成器产出）；README 只写事实与替代安装方式，**不写账号原因**；已装旧名用户走 GitHub tag 更新路径，不要留死路。

### 5.7 账号与凭据治理

- 2FA **必须备份恢复码**；记录在密码管理器里。
- 账号找回材料（工单、身份验证、客服往返）只存私有文件，**绝不入公开仓库**。
- 身份验证正路：平台官方提供的所有权证明流程（如 secret gist + 另一可控账号的关联证据），不要伪造材料。

### 5.8 发布物与发布流水线

**发布物清单必须逐条看**

- `npm pack --dry-run` 只是「打印清单」，**不是「看过清单」**：必须逐条核对，确认没有内部审查报告、过程材料、账号语境、失败现场、截图、`.npmrc`。
- `docs/` 与 `.github/` **不得进包**；内部审查报告属于过程材料，公开了也撤不回。
- `tools/` 默认不进包，**唯一例外**是运行时安装器（宿主安装时必须 spawn 它）—— 除这一个文件外出现任何 `tools/*` 都判红；同时发布面断言必须**正向**确认它在包里（只允许不存在的单向检查会在误删后全绿）。
- 白名单是「允许列表」：往已列入的目录里新塞文件不会自动被拦，仍要人看清单；发布包文件数应落在合理区间（本仓区间见 annex）。

**暂存多版本时只批最新**

- 暂存区可能同时躺着多个版本（重试、补发、误操作都会留下）；**只批最新那一个**。
- 批之前核对：版本号 = 本次要发的；tag 指向的 commit = 暂存产物的 commit；`dist-tags` 的 `latest` 没被上一次的暂存提前推动。

**发布 workflow 的三条硬约束**

1. **默认走暂存，不默认直接发布**：推 tag → 暂存发布；批准（2FA / WebAuthn）是**人**在 npm 网页上的一次点击。CI 里不自动批准、不用 token 绕过 2FA。
2. **`npm install -g npm@latest` 必须放在 `setup-node` 之后**：新版 npm 的暂存命令需要较新 npm，而 `setup-node` 会安装 / 覆盖 node 与 npm；写在它之前会被覆盖，症状是「未知命令」。
3. **绑定页的 Allowed actions 必须与 workflow 分支一致**：默认暂存 → 必须允许暂存发布动作；手动直接发布 → 才需要额外允许直接发布。不一致的典型症状是 404（不是包名写错，是没被认成 trusted publisher）；provenance 签名成功**不代表**认证成功。

**自动防线（现状）**：workflow 契约测试断言 —— 默认暂存且保留直接发布分支（锚定 `run:`，不匹配注释文字）、安装 → 测试 → 构建 → 暂存发布的**顺序**、`id-token: write`、action 固定大版本 tag、无 tab、`npm install -g npm@latest` 在 `setup-node` 之后；发布面断言负责白名单与运行时安装器存在性。

**仍是人工的**：绑定页 Allowed actions 只能在网页核对；「只批最新」没有机械检查；暂存产物与 tag 的对应关系要人核。

## 6. 环境与工具链

1. **registry 可能是镜像**：装包显式指定官方源；CI 用官方源。
2. **构建工具禁止装 `/tmp`**：系统会清理，软链悬空后构建静默失败而烟测测旧产物。统一装在持久目录，构建失败必须显式报错。
3. **`pnpm add/install` 会清掉手工链接的宿主包**：平台包来自宿主本体，不在公共 registry 的同一位置。任何依赖变更之后必须重跑本仓的链接 / setup 步骤，否则自检会报「schema 加载失败」。
4. **github.com 网络不稳**：push 失败（`Empty reply` / HTTP2 framing）时改用 HTTP/1.1 + 重试；把重试交给后台 / 脚本跑到成功并留日志，**不要手工反复**（§3.2.14）；权限 / 认证失败不可重试，立刻停。
5. **看到 `disabling profile plugin row` 的正确解读**：profile 里出现旧版 `@deepseek-ai/*` 副本时，宿主闸门会 disable 关键行，但报错只说下游 waiting。处置顺序：① 直跑 host 拿 stderr（别只看 crash 日志）；② 看 profile 顶层有没有 `@deepseek-ai/*`；③ 有 → 某个插件带了硬依赖（§2.7），修正或卸载它；④ 临时对齐版本只能止血，不修插件下次还会复发。
6. **`node` 可能不在 PATH**（DSH 桌面端常态）：用捆绑 node 的绝对路径跑脚本；本仓路径见 annex。
7. **本机特有的坑**（镜像版本、工具目录、历史路径）记在 annex，不要写进共享正文。

## 7. 文档与留痕 / 规范维护

### 7.1 文档分工

- `README.md`：面向用户（是什么、装什么、怎么用、不同点）。
- `docs/` 下设计定稿：面向自己（取舍过程、定稿版本）。
- `CHANGELOG.md`：面向升级用户（可感知变化 + 迁移提示）。
- `docs/reviews/`：每次复盘 / 评审一篇（症状、根因、防线、还差什么）。
- 事故总账：面向自己与下一位 agent（症状 / 根因 / 影响面 / 怎么发现 / 修复 / 防线 / 报告）；**新事故先写总账，再改规范，再加断言**。总账位置与索引见 annex。
- 内部调查笔记（竞品、账号、排查过程）→ **私有目录**，不入公开仓库。

### 7.2 spec 政策（哪些改动必须先写 spec）

**必须先写一页 spec**（模板见本仓 `docs/specs/`）：

- 跨会话 / 跨重启的数据模型或存储 schema 变更；
- 安装 / 升级 / 自更新 / 权限路径；
- 对外发布流程、包名、鉴权方式变更；
- 口径类功能（数据来源、算法、允许误差）；
- 验收标准无法用现有测试表达的改动。

**可只写 review 记录**：纯 UI 微调、文案、布局、单点 bug 修复。
spec 的验收标准必须**可执行**（命令 / 截图 / 对账），无法自动验证的条目单独标注「人工检查」并写明由谁看。

### 7.3 规范自身的维护

- **单一事实源**：正文只在共享部分维护，仓库差异只进 annex；改共享正文必须两仓同改（文档门禁跨仓校验）。
- **引用自动校验**：文档里新增路径 / 脚本 / 命令前，先让它们存在；文档门禁会把不存在的引用报成红。
- **版本与变更记录**：每次实质修改升次版本号并写变更记录（本文件头部）。
- **评审周期**：每次跨仓同步后、或每季度做一次「规范 vs 实际闸门」对账；审计发现的偏差必须落成「改文档」或「补断言」之一，不许只记在脑子里。
- **废弃条款机制**：删条款用 `~~删除线~~ + 日期 + 原因 + 替代条款` 的方式保留一行痕迹，不要直接消失（下一位读者需要知道它曾经存在、为什么被删）。
- **状态图例**：✅ 自动（有断言且做过反向验证）/ ⚠️ 半自动或手工 checklist / ❌ 缺口。**手工 checklist 不许写成「已拦住」。**
